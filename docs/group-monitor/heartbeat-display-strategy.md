# 心跳格展示策略

## 当前实现：方案 A（按次数展示）

### 逻辑
- 60 格 = 最近 60 条测试记录（无论来源）
- 每格间隔不固定，取决于数据密度
- 悬浮 Tooltip 显示具体时间（`formatTimeAgo`）

### 数据来源混合
| 来源 | 触发频率 | 说明 |
|------|---------|------|
| 用户真实请求 | 最快 30 秒/次（sync.Map 限流） | 高频渠道密集 |
| 定时主动测试 | 每 30 分钟/次 | 低频渠道稀疏 |

### 覆盖时间范围（不固定）
- 高频渠道（用户请求多）：60 格 ≈ 最近 **30 分钟**
- 低频渠道（只有主动测试）：60 格 ≈ 最近 **30 小时**

### 优点
- 实现简单，直接取最近 60 条
- 尽可能反映最新状态

### 缺点
- 不同渠道格子时间跨度不一致，横向对比意义弱
- 格子之间间隔不均匀，视觉上可能误导

## 备用方案：方案 B（固定时间窗口聚合）

> 参考 Uptime Kuma 的做法，后续如需优化可切换为此方案。

### 逻辑
- 60 格，每格代表固定时长 = **主动测试间隔**（如 30 分钟）
- 覆盖范围：60 × 30分钟 = **最近 30 小时**
- 一个窗口内有多条记录时，取**最差状态**作为格子颜色：
  - 有红色（全失败）→ 红色
  - 有橙色 → 橙色
  - 有黄色 → 黄色
  - 全绿 → 绿色
  - 无数据 → 灰色

### 后端聚合 SQL 示意
```sql
-- 按时间窗口分桶，每桶取最差状态
SELECT
  FLOOR(tested_at / 1800) AS bucket,  -- 1800 = 30分钟
  channel_id,
  MIN(CASE WHEN success = false THEN 0 ELSE 1 END) AS any_failure,
  MIN(response_time) AS min_rt,
  MAX(response_time) AS max_rt
FROM channel_test_histories
WHERE channel_id IN (?, ?, ?)
  AND tested_at >= UNIX_TIMESTAMP() - 60 * 1800
GROUP BY bucket, channel_id
ORDER BY bucket DESC
LIMIT 60
```

### 前端变化
- 每格宽度相同，时间间隔一致
- Tooltip 显示"该窗口时间范围"而非单次时间
- 灰色格子表示该时间窗口内无数据（如凌晨低峰期）

### 优点
- 各分组时间轴对齐，横向可对比
- 视觉直观，类似 Uptime Kuma
- 充分利用用户请求数据（窗口内有数据就不用等主动测试）

### 缺点
- 需要按时间窗口聚合，后端逻辑稍复杂
- 窗口大小与测试间隔耦合（间隔改了窗口也要改）
- 凌晨低峰期可能出现灰色格子

### 切换方式
1. 后端 `GetGroupMonitorStatus` 改为按 bucket 聚合，返回 `bucket_start`、`bucket_end` 字段
2. 前端 `HeartbeatGrid` 改为固定 60 个格子，无数据的桶填灰色
3. `HeartbeatRecord` 新增 `bucket_start: number`、`bucket_end: number` 字段

## 当前配置参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 心跳格数量 | 60 | 展示最近 60 条记录 |
| 用户请求写入限流 | 30 秒 | 同一渠道 30 秒内最多写一次 |
| 定时测试间隔 | 30 分钟（可配置） | 无用户请求时的兜底测试 |
| 历史保留上限 | 100 条/渠道 | 超出自动清理旧数据 |
