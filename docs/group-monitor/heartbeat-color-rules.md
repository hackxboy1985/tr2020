# 分组监控心跳格颜色规则设计

## 1. 核心设计理念

心跳格不仅反映"是否可用"，更要反映**系统降级程度**。通过颜色区分：
- 🟢 绿色：最佳状态（高优先级渠道正常）
- 🟡 黄色：降级运行（高优先级挂了，中优先级顶上）
- 🟠 橙色：严重降级（前2个优先级都挂了，仅低优先级可用）
- 🔴 红色：完全故障（所有渠道都不可用）

---

## 2. 渠道优先级分层

### 2.1 取前 3 个优先级最高的渠道

**示例分组**：
```
渠道2: priority=100  (高优先级)
渠道1: priority=50   (中优先级)
渠道3: priority=10   (低优先级)
渠道4: priority=5    (更低，不考虑)
```

**代表渠道集合**：取前 3 个 → [渠道2, 渠道1, 渠道3]

### 2.2 颜色判断规则

每个心跳格（对应一个测试时间点）的颜色由**前3个优先级渠道**在该时间点的测试结果决定：

| 高优先级 | 中优先级 | 低优先级 | 颜色 | 状态说明 |
|---------|---------|---------|------|---------|
| ✅ 成功 | - | - | 🟢 **绿色** | 最佳状态 |
| ❌ 失败 | ✅ 成功 | - | 🟡 **黄色** | 降级运行（中优先级顶上） |
| ❌ 失败 | ❌ 失败 | ✅ 成功 | 🟠 **橙色** | 严重降级（仅低优先级可用） |
| ❌ 失败 | ❌ 失败 | ❌ 失败 | 🔴 **红色** | 完全故障 |

**优先级顺序判断**：
1. 先看最高优先级（渠道2）是否成功 → 成功则 🟢 绿色
2. 若最高失败，看中优先级（渠道1）→ 成功则 🟡 黄色
3. 若前2个都失败，看低优先级（渠道3）→ 成功则 🟠 橙色
4. 若3个都失败 → 🔴 红色

## 3. 特殊场景处理

### 3.1 分组只有 2 个渠道

**示例**：
```
渠道2: priority=100  (高)
渠道1: priority=50   (中)
```

**规则**：
| 高优先级 | 中优先级 | 颜色 | 状态 |
|---------|---------|------|------|
| ✅ 成功 | - | 🟢 绿色 | 最佳 |
| ❌ 失败 | ✅ 成功 | 🟡 黄色 | 降级 |
| ❌ 失败 | ❌ 失败 | 🔴 红色 | 故障 |

**说明**：跳过橙色（因为没有第3个渠道）

---

### 3.2 分组只有 1 个渠道

**示例**：
```
渠道1: priority=50
```

**规则**：
| 渠道状态 | 颜色 |
|---------|------|
| ✅ 成功 | 🟢 绿色 |
| ❌ 失败 | 🔴 红色 |

**说明**：只有绿/红两种状态，无降级概念

---

### 3.3 分组有 4+ 个渠道

**示例**：
```
渠道5: priority=200  (最高)
渠道2: priority=100  (高)
渠道1: priority=50   (中)
渠道3: priority=10   (低)
渠道4: priority=5    (更低)
```

**规则**：只取前 3 个 → [渠道5, 渠道2, 渠道1]

| 渠道5 | 渠道2 | 渠道1 | 颜色 |
|------|------|------|------|
| ✅ | - | - | 🟢 绿色 |
| ❌ | ✅ | - | 🟡 黄色 |
| ❌ | ❌ | ✅ | 🟠 橙色 |
| ❌ | ❌ | ❌ | 🔴 红色 |

**说明**：渠道3 和渠道4 不参与颜色判断

## 4. 数据结构设计

### 4.1 后端查询逻辑

```sql
-- 1. 查出该分组所有渠道，按优先级降序
SELECT channel_id, priority 
FROM abilities 
WHERE group = ? 
ORDER BY priority DESC, channel_id ASC;

-- 2. 取前 3 个作为"代表渠道集合"
top3_channels = [channel_id_1, channel_id_2, channel_id_3]

-- 3. 对每个时间点，查询这 3 个渠道的测试结果
SELECT channel_id, success, tested_at 
FROM channel_test_histories 
WHERE channel_id IN (?, ?, ?) 
  AND tested_at >= ? 
ORDER BY tested_at DESC;

-- 4. 按时间点分组，计算每个时间点的颜色
GROUP BY tested_at:
  - 如果 channel_id_1 成功 → 绿色
  - 否则如果 channel_id_2 成功 → 黄色
  - 否则如果 channel_id_3 成功 → 橙色
  - 否则 → 红色
```

## 7. 可用率计算

### 7.1 基于颜色的加权可用率

**方案 A：二元计算（简单）**
```
可用率 = (绿色+黄色+橙色) / 总格数
故障率 = 红色 / 总格数
```

**方案 B：加权计算（更精确）**
```
健康分数 = (绿色×1.0 + 黄色×0.7 + 橙色×0.4 + 红色×0.0) / 总格数
```

**推荐**：方案 A（简单直观），因为只要有渠道能用就算"可用"。

### 7.2 展示示例

```
可用率: 92.3%  (绿色: 70%, 黄色: 20%, 橙色: 2.3%, 红色: 7.7%)
```

## 8. 实现伪代码

```go
func calculateHeartbeatColor(top3Channels []int, testResults map[int]bool) string {
    // top3Channels: [渠道2(p=100), 渠道1(p=50), 渠道3(p=10)]
    // testResults: {2: false, 1: true, 3: true}
    
    // 按优先级顺序判断
    for i, channelID := range top3Channels {
        if success, exists := testResults[channelID]; exists && success {
            switch i {
            case 0:
                return "green"   // 高优先级成功
            case 1:
                return "yellow"  // 中优先级成功（高失败）
            case 2:
                return "orange"  // 低优先级成功（前2个失败）
            }
        }
    }
    
    // 所有渠道都失败
    return "red"
}
```

## 9. 优势总结

### 相比单渠道方案的优势

**原方案**：只看代表渠道（最高优先级 enabled=true）
- ❌ 高优先级挂了自动切到中优先级，心跳格从红变绿，看不出降级
- ❌ 无法区分"完全健康"和"降级但可用"

**新方案**：综合前3个优先级渠道
- ✅ 颜色直观反映降级程度
- ✅ 管理员能立即看出哪个优先级层出问题
- ✅ 符合实际调度逻辑（retry 时会降级到低优先级）

## 10. 待确认问题

1. **渠道数量不足3个时，橙色的定义**：
   - 如果只有2个渠道，是否需要橙色？
   - 建议：2个渠道 = 绿/黄/红，无橙色

2. **同优先级多个渠道**：
   - 如果有3个渠道都是 priority=100，如何处理？
   - 建议：按 channel_id 排序，取前3个

3. **时间对齐问题**：
   - 3个渠道的测试时间可能不完全一致（差几秒）
   - 建议：按测试轮次对齐（每轮定时测试生成一个统一时间戳）
